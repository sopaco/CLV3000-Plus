# 系统边界接口

CLV3000 Plus 是一款纯粹的图形界面桌面应用——它的对外界面只有两类：原生窗口（8 个功能页）和系统托盘。没有命令行、没有网络服务、没有插件系统，用户对能力的所有触发都被收敛到这两条入口上。这种"接口极简"不是功能缺失，而是刻意的架构克制：一个负责删除用户文件的工具，暴露面越少，可被误触、误注入、被威胁的渠道就越少。理解边界接口，就是理解"用户能从哪里按下一个按钮、系统往哪里写出一份文件"，本文件将逐一列出这些人际边界和机际边界。

## 1. 图形用户界面

界面的主体是一个主窗口（默认 1280×720，居中）加自定义标题栏，由 `AppShell`（`crates/clv-app/src/app/shell.rs`）承载，内部按 `AppPage` 枚举（`crates/clv-app/src/app/state.rs`）切换 8 个页面。页面采用"惰性实体"模式：`ClvApp` 只在第一次切到某页时才创建该页的 `Entity` 并缓存，避免启动时一次性构造所有视图拖慢首屏。查看页面时的进度反馈由 `ProgressHud`（`crates/clv-app/src/app/hud.rs`）以全局面板形式覆盖渲染，不占用任何页面的布局空间。

| 页面 | 枚举变体 | 视图文件 | 职责 |
|------|---------|----------|------|
| 首页 | `AppPage::Dashboard` | `crates/clv-app/src/views/dashboard.rs` | 磁盘用量分布、扫描概览、最近清理记录、回收区恢复入口 |
| 智能清理 | `AppPage::Cleanup` | `crates/clv-app/src/views/cleanup.rs` | 扫描项列表，支持安全/分类筛选与关键词搜索，勾选后执行清理 |
| Agent 项目 | `AppPage::Agent` | `crates/clv-app/src/views/agent.rs` | 展示 `detect_agent_projects` 识别的 AI 残留项目及结构化原因 |
| 启动项管理 | `AppPage::Startup` | `crates/clv-app/src/views/startup.rs` | 枚举系统登录启动项，供优化开机速度参考 |
| 进程管理 | `AppPage::Process` | `crates/clv-app/src/views/process.rs` | 基于 sysinfo 列出进程，支持搜索、排序与终止 |
| 大文件 | `AppPage::LargeFiles` | `crates/clv-app/src/views/large_files.rs` | 独立于规则的超大文件清单，解释"项目为什么这么大" |
| 设置 | `AppPage::Settings` | `crates/clv-app/src/views/settings.rs` | 编辑 `AppSettings` 全量配置（扫描路径、软删除、语言、主题） |
| 欢迎 | `AppPage::Onboarding` | `crates/clv-app/src/views/onboarding.rs` | 首次运行向导（`settings.onboarding_done == false` 时自动进入） |

## 2. 系统托盘

系统托盘（`crates/clv-app/src/tray.rs`）是窗口之外唯一的常驻入口，基于 `tray-icon` + `muda` 实现：macOS 上是菜单栏图标，Windows 上是通知区托盘图标。托盘承担三类职责：打开主窗口、从任意状态触发一次扫描、退出应用。托盘事件不直接驱动 UI，而是先写入一个共享槽位 `TrayPending`，由主循环每 250ms 轮询拾取后转交 `AppStore` 处理——这样托盘线程永远不需要碰 GPUI 的 UI 状态，避免跨线程数据竞争。

| 动作 | 触发方式 | 转发目标 | 含义解读 |
|------|---------|----------|----------|
| 打开（Open） | 点击菜单项，或双击托盘图标 | `TrayAction::Open` → `ensure_main_window` | 窗口已存在则激活，不存在则重建；托盘是"找回窗口"的最短路径，因为窗口可能被用户随手关掉而进程仍在托盘存活 |
| 扫描（Scan） | 点击菜单项 | `request_scan()` 置位原子标志 → `start_scan` | 用 `AtomicBool SCAN_REQUESTED` 独立于菜单事件流传递扫描请求，即便主窗口尚未打开，请求也不会丢；主循环每 250ms 检查一次并启动扫描 |
| 退出（Quit） | 点击菜单项 | `TrayAction::Quit` → `cx.quit()` | 显式的全局退出入口，与关闭窗口（仅关窗口、进程仍驻留）语义区分 |
| 动态提示 | 磁盘用量刷新时 | `TrayController::set_global_tooltip` | 托盘 tooltip 每轮磁盘用量采集后更新为"已用百分比"，让用户不打开应用也能瞥见磁盘水位 |

## 3. 快捷键

应用的快捷键面刻意保持最小——只有一条全局绑定：关闭窗口。`init_window_close_shortcuts`（`crates/clv-app/src/main.rs`）注册了两个按键绑定：`cmd-w`（macOS 平台修饰键）与 `secondary-w`（Windows/Linux 上映射为 Ctrl + W），共同触发 `CloseWindow` action。

这里的语义需要澄清：快捷键关闭的是**窗口**，不是退出应用。关闭后进程继续留在系统托盘，用户随时可凭托盘图标找回窗口——这与 macOS 的"红点关窗不留进程"习惯一致，也让托盘"打开（Open）"入口有了存在的意义。为保险起见，`intercept_keystrokes` 还在 action 未消费按键时做了一次兜底拦截，确保任何聚焦状态下 Cmd/Ctrl+W 都能关窗，而不是被焦点控件吞掉。

| 按键 | action | 行为 |
|------|--------|------|
| Cmd+W（macOS）/ Ctrl+W（Windows/Linux） | `CloseWindow` | 关闭当前活动主窗口，进程保持托盘驻留 |

## 4. 配置结构

全部配置收敛在单个 `AppSettings` 结构体（`crates/clv-core/src/settings/mod.rs`）中，持久化为 `settings.json`。字段设计遵循"能枚举就不自由、能开关就不猜测"的原则：路径类字段用向量允许任意多个，布尔类字段全部给出保守默认值，避免任何"开箱即删"的危险行为。

| 配置项 | 类型 | 默认值 | 含义解读 |
|--------|------|--------|----------|
| `scan_paths` | `Vec<PathBuf>` | 常见开发目录（`~/Projects`、`~/Documents`、`~/Desktop`、`~/dev` 等） | 扫描的根目录集合；默认值覆盖主流开发者的习惯布局，但用户可增删。仅扫描白名单、绝不整盘扫描，是"宁可漏扫不可误扫"的边界声明 |
| `expert_mode` | `bool` | `false` | 是否放行 `RiskLevel::Protected`（工具链等）条目的清理；默认关闭，因为它把"删错了会坏环境"的风险从系统转移到用户判断力上 |
| `soft_delete` | `bool` | `true` | 删除走回收区（移动）而非直接销毁；这是整个应用安全模型的第一道门，默认开启意味着误删永远有后悔药 |
| `soft_delete_days` | `u32` | `7` | 回收区条目保留天数，超期由 `purge_old_trash` 清除；7 天是"够你发现数据丢失并找回"与"别让回收区无限膨胀"之间的折中 |
| `include_agent_heuristics` | `bool` | `true` | 是否启用 Agent 项目检测与会话发现；这是差异化功能的总开关，关闭后系统退化为普通磁盘清理器，用户可自主选择是否接受启发式判断 |
| `auto_scan_weekly` | `bool` | `false` | 每周自动扫描空开（当前为保留的调度开关，默认关闭）；自动行为方默认启用权交给用户，避免未经许可的后台磁盘遍历 |
| `onboarding_done` | `bool` | `false` | 是否已完成首次向导；控制启动页是进 Welcome 还是直接进 Dashboard |
| `language` | `LanguagePreference` | 系统语言 | 三语界面（中/英/日）偏好，驱动 `resolve_language` |
| `theme` | `ThemePreference` | 默认主题 | 四套配色方案（Defender / Blossom / Neon / Aurora），启动时经 `apply_theme` 注入 |

路径解析层面还有两个隐含约定：扫描路径支持 `~` 展开（`expand_scan_path`），Windows 下额外支持 `%VAR%` 环境变量展开；所有受保护系统路径（Unix 的 `/`、`/System`，Windows 的 `%SystemRoot%` 等）由 `is_protected_system_path` 硬编码拦截，任何扫描、清理阶段看到这些路径都会直接跳过。

## 5. 清理规则系统

清理规则是扫描器的"分拣手册"，全部以类型化的 `CleanupRule`（`crates/clv-core/src/settings/rule.rs`）静态声明。每条规则描述"一个目录、属于哪个技术栈、风险多高、归入哪个分类"，并提供三个可选的门控字段（`requires_marker` / `relative_prefix` / `requires_parent`），让规则既能匹配精确目录名（`target`）、也能匹配前缀（`cmake-build-*`）或后缀（`*.egg-info`）、还能限定父目录，从而实现"同样的目录名在不同技术栈下有不同处置"的精准分拣。

规则库分两类，由 `crates/clv-core/src/settings/project_rules.rs`（60+ 条，覆盖 17 种技术栈）和 `crates/clv-core/src/settings/global_rules.rs`（30+ 条，按平台分叉）提供：

| 规则库 | 数量与覆盖 | 典型条目 | 设计意图 |
|--------|-----------|----------|----------|
| 项目级规则 `project_rules()` | 60+ 条，覆盖 Rust、Node/Web、Python、Java、Go、Android、iOS、Flutter、.NET、C++、Ruby、PHP、KMP、Unity、Infra 等 17 种技术栈 | `target`（需 `Cargo.toml` 标记）、`node_modules`（需 `package.json`）、`.next`、`.venv`、`build/`、`DerivedData` | 项目的构建产物/依赖必须在"项目根内"才成立，故借标记文件（`Cargo.toml`、`package.json`）确认项目身份；名称命中后只扫描、不深入子目录，防止误删源码 |
| 全局规则 `global_cache_rules()` | 30+ 条，`#[cfg(target_os = "windows")]` 与非 Windows 两个分支各维护一份 | `~/.cargo/registry/cache`、`.npm/_cacache`、`$LOCALAPPDATA/pnpm/store`、`~/.rustup/toolchains`、浏览器缓存 | 全局缓存与平台目录习惯强相关（Windows 走 `$LOCALAPPDATA`/`$APPDATA`，macOS 走 `~/Library/Caches`），故按平台分叉；其中工具链（toolchains、pyenv 版本）标为 `Protected`，只在专家模式下放行 |

`CleanupRule` 的完整结构如下表：前五个字段是规则的"身份证"，后三个可选字段是它的"门禁规则"。

| 字段 | 类型 | 含义解读 |
|------|------|----------|
| `relative` | `&'static str` | 规则命中的目录名（相对项目根或全局路径），是分拣手册的"条目名" |
| `stack` | `TechStack` | 归属技术栈，决定该条目在 UI 上显示为什么类型的产物 |
| `risk` | `RiskLevel` | `Safe` / `Caution` / `Protected` 三档，直接决定默认是否预选、是否可操作 |
| `category` | `CleanupCategory` | 类型化清理分类，经由 `cleanup_bucket` 映射到四个 `CleanupBucket` 桶，驱动 UI 侧栏过滤 |
| `description` | `RuleDescription` | 三语描述型枚举（`R001`…`R133`），由翻译表自动生成，不在领域层硬编码文案 |
| `global` | `bool` | 规则属于全局缓存库（`global_rules.rs`）还是项目库（`project_rules.rs`） |
| `requires_marker` | `Option<&'static str>` | 项目根目录须存在该标记文件（支持 `*.ext` glob 后缀匹配），防止"恰好叫 target 的普通目录"被误抓 |
| `relative_prefix` | `Option<&'static str>` | 名称前缀（`cmake-build-`）或后缀（`*.egg-info` → 以 `.egg-info` 结尾）模式的目录名匹配 |
| `requires_parent` | `Option<&'static str>` | 父目录名必须匹配（如 Ruby 的 `vendor/bundle` 要求父目录是 `vendor`），消解同名目录歧义 |

规则库是纯静态的 `LazyLock` 常量，运行时不可增删。这条约束保证了：规则永远可预测、可测试、可审计，与运行时数据完全解耦——用户可以把规则表当作"文档"来读，而不是猜测某些规则是否被动态篡改。

## 6. 环境变量

Agent 会话发现（`crates/clv-core/src/agent_sessions.rs`）依赖六个环境变量来定位各 AI 工具的会话/缓存目录。这些变量的处置遵循同一模式：**读取环境变量，若未设置则回退到平台默认路径**。这样既尊重用户"把工具数据搬到别处"的自定义，又保证零配置即可开箱即用。若用户显式设置了多个路径（逗号分隔），系统会全部纳入扫描。

| 环境变量 | 作用 | 默认回退路径 |
|----------|------|--------------|
| `CODEX_HOME` | Codex 会话根目录 | `~/.codex` |
| `CLAUDE_CONFIG_DIR` | Claude 配置根目录，定位 `projects/` 会话 | `~/.claude`、`~/.config/claude` / `%APPDATA%\Claude` |
| `CODEBUDDY_HOME` | CodeBuddy / WorkBuddy 数据根目录 | `~/.codebuddy` |
| `TRAE_DIR` | Trae 数据目录（User 父级），解析其 `CachedData`、`GPUCache`、`workspaceStorage` 等 | 按平台目录自动发现（`~/Library/Application Support/Trae` 等） |
| `TRAEX_SESSIONS_DIR` | Trae CLI（TraeX）会话根目录 | `~/.trae/cli` |
| `OPENCODE_DIR` | OpenCode 数据目录，定位 `log`、`project`、`storage` | `~/.local/share/opencode`（并参考 `XDG_DATA_HOME`） |

除上述六个定位变量外，全局规则库的路径解析还会用到平台变量 `%LOCALAPPDATA%` / `%APPDATA%`（Windows）、`$TEMP` / `$TMP`、`~` 与 `%USERPROFILE%`（见 `crates/clv-core/src/paths.rs` 的 `resolve_global_path`）。这些变量的解析全部走 `Option`/`ok()` 链，任一变量缺失仅导致对应规则被跳过，绝不会因环境变量不存在而让整个应用崩溃。

## 7. 持久化文件

CLV3000 Plus 采用"文件即数据库"策略，全部状态落在三个 JSON 文件加一个回收区目录里，位于操作系统标准配置目录（macOS `~/Library/Application Support`、Windows `%APPDATA%`、Linux XDG 路径）。无数据库设计让状态对人类完全透明——任何文件都可直接打开查看，损坏时统一回退到默认/空态（见"错误处理策略"），用户永远拿得到可用应用。

| 文件 | 内容 | 写入时机 | 含义解读 |
|------|------|----------|----------|
| `settings.json` | `AppSettings` 全部配置 | 用户修改设置时 | 长期偏好，永久保留；启动时 `load_settings` 读取，损坏则回退默认值 |
| `last_scan.json` | `ScanReport` 最近一次完整扫描快照 | 每次扫描完成时覆盖写 | "空窗期即时数据"的载体——未扫描时 Dashboard 展示的就是这份缓存，避免用户刚打开应用时对着空白发呆 |
| `cleanup_history.json` | `CleanupHistory` 清理记录（含 `TrashedEntry`） | 每次清理完成后追加 | 审计与回溯：按 `timestamp` 维护 90 天滚动窗口，`freed_in_days` 等统计方法由此得出；删除条目被 `remove_trashed` 同步移除 |
| `trash/` | 软删除移动来的原始文件 | 清理执行时 `move_entry` 移入 | 误删安全网：条目命名带时间戳与随机 UUID 避免冲突；`purge_old_trash(soft_delete_days)` 在应用启动后清理过期条目，`restore_trashed` 支持按 `TrashedEntry` 原样搬回 |

## 8. 集成建议

在"纯 GUI + 本地文件"的架构约束下，CLV3000 Plus 仍为自动化留出了几条低成本、非侵入的接缝，适合脚本、CI 或系统运维工具调用：

1. **环境变量驱动发现**：定位 Agent 工具目录的六个环境变量（第 6 节）同样可被外部侧脚本复用——只要为会话目录另行分配 `CODEX_HOME` 等路径，扫描就能与"迁移了工具数据的机器"协同，无需改任何配置文件。
2. **JSON 状态可直接机器读取**：`cleanup_history.json` 与 `last_scan.json` 都是结构化 JSON，运维脚本可定期解析其中的 `freed_bytes`、`success_count`、`failed_count` 做容量报告或告警，不必一定打开 GUI。
3. **托盘扫描作为外部触发器**：从外部命令行往应用的"托盘语义"注入扫描请求（如通过启动时 `take_scan_request()` 标志位扩展）即可实现"开机自动扫一次"的无人值守场景——当前 `auto_scan_weekly` 已预留调度开关，未来可直接接线到该标志位。
4. **回收区可被文件系统工具快照**：`trash/` 目录是普通文件夹，备份工具只需排除它即可避免把"待删垃圾"也备份一遍；反之，运维侧也可在清理前先 tar 该目录做离线快照，获得比 7 天回收期更长久的后悔药。

无论哪种集成方式，都应遵循系统的一条底线：**配置、历史、回收区属于应用，而文件删除的最终裁决永远属于用户**——任何脚本接入都建议以只读读取为主，把写操作留给人或显式授权的任务。
