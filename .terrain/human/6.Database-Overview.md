# Database Overview

CLV3000 Plus does not use a relational database, ORM, or embedded SQL engine. That choice matches the product's scope: scan results are ephemeral session data, and the only long-lived configuration is a small JSON preferences file. Understanding this persistence model explains why there is no migration folder, no connection string, and no query layer in the codebase.

## How Data Is Stored Instead

| Data | Storage | Location / Mechanism |
|------|---------|----------------------|
| User preferences | JSON file | `settings.json` via `settings_path()` in `crates/clv-core/src/settings.rs:41-44` |
| Soft-deleted files | Filesystem directory | `trash/` under app data local dir (`settings.rs:83-86`) |
| Scan results | In-memory only | `AppStore.last_report` in `crates/clv-app/src/app/state.rs:64` — not persisted between app restarts |
| Startup/process lists | Live OS queries | sysinfo, registry, launchctl — no local cache |

When the user closes the app, reclaimable item lists are discarded. The next scan rebuilds `ScanReport` from scratch, which keeps storage simple and avoids stale path references after external deletes.

## Why No Database

A cleanup utility that walks arbitrary user directories does not need transactional storage for scan hits—the filesystem is the source of truth. Adding SQLite would increase binary size, complicate migrations, and duplicate path metadata already on disk. Settings JSON is human-editable for power users who want to script `scan_paths`.

## If You Need Historical Scan Data

That would be a future product extension (e.g. export scan JSON, or optional SQLite audit log). Current code has no schema for scan history; `ScanReport` is `Serialize` (`models.rs:213`) so export could be added without a DB.

## Summary

| Type | Count |
|------|-------|
| Tables | 0 |
| Views | 0 |
| Migrations | 0 |

Persistence = **settings JSON + optional trash folder + live OS APIs**.
